# Chat intent, conversation context, and store catalog

## Catalog audit

The storefront had no product API, backend product model, or database. Its six catalog entries were a JavaScript array in `frontend/src/pages/Products.jsx`. That exact data now lives in `shared/products.json`, imported by the storefront and validated/read by `ProductCatalogService` in the backend. This avoids a second catalog.

The actual product fields are `id`, `name`, `category`, `price`, `rating`, `image`, `description`, `ingredients`, and `skin`. There is no stock/availability field, so responses never claim stock. Skin compatibility and ingredients are only filtered/displayed from those existing fields.

## Routing and response behavior

- `source_request` is checked before symptom cues. It returns title, publisher, and URL from retrieved verified documents; it never calls fuzzy inference or invents a citation.
- `product_recommendation` and `product_search` run deterministic category, ingredient, and catalog `skin` filters. The backend returns validated `products` alongside the existing `reply` field. Product facts are never generated by Ollama.
- `skin_analysis` alone enters lexicon extraction/Fuzzy Mamdani. `skin_information` and `general_skincare` use the evidence pipeline.
- Product cards show the actual image/name/category/price/description/skin metadata, link to the matching existing product detail modal (`/produk?product=<id>`), and call the existing cart context.

## Conversation context

The frontend sends a UUID conversation ID and at most six recent user/assistant turns. The backend keeps no session state. Product IDs attached to prior assistant turns are resolved against the current catalog before a product follow-up can use them. Unknown IDs are discarded. New Conversation resets the local history and ID, and an older in-flight response is ignored after that reset.

History roles and lengths are schema-validated. History is included only as conversational context in educational prompts; it is never evidence. Retrieval uses current and recent user turns. Product follow-ups use catalog IDs and deterministic templates rather than assistant history text.

## Verification

`cd backend && python -m unittest discover -s tests -v` covers intent examples, source requests, catalog/category/ingredient/skin filtering, missing catalog data, product follow-ups, history bounds, API serialization, and preservation of the cart-compatible product schema.
